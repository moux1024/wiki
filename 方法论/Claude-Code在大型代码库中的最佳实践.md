## Claude Code 如何导航大型代码库

Claude Code 像软件工程师一样导航代码库：遍历文件系统、读取文件、使用 grep 精确定位、跨代码库追踪引用。它在开发者本地机器上运行，**不需要构建、维护或上传代码库索引**。

### RAG vs Agentic 搜索

RAG 驱动的 AI 编码工具通过嵌入整个代码库并在查询时检索相关片段工作。在大规模场景下，这类系统容易失败——嵌入流水线无法跟上活跃工程团队的节奏。当开发者查询索引时，索引反映的可能是一周前、几天前甚至几小时前的代码状态。

Agentic 搜索（Claude Code 的方式）避免了这些失败模式。没有嵌入流水线或集中式索引需要维护。每个开发者实例直接从活代码库工作。

**代价是**：Claude 需要足够的起始上下文才知道去哪里找。导航质量取决于代码库的设置质量——通过 CLAUDE.md 文件和 skills 层叠上下文。

## Harness 与模型同等重要

Claude Code 的能力**不仅由模型定义**，围绕模型构建的生态系统（harness）在实际使用中影响更大。Harness 由五个扩展点构成：

### 1. CLAUDE.md — 上下文文件

- 根目录文件提供全局视图，子目录文件提供局部约定
- Claude 自动在每次会话开始时读取
- **关键原则**：保持精简，只放广泛适用的内容
- Claude 会沿目录树向上遍历，加载沿途所有 CLAUDE.md 文件

### 2. Hooks — 让设置自我改进

- 大多数团队将 hooks 视为防止错误的脚本，但其更有价值的用途是**持续改进**
- **Stop hook**：在会话结束时反思，提议 CLAUDE.md 更新
- **Start hook**：动态加载团队特定的上下文
- 对于 lint/format 等自动化检查，hooks 确定性地执行规则，效果比让 Claude 记住指令更好

### 3. Skills — 按需加载专业知识

- 通过**渐进式披露**（progressive disclosure），只在任务需要时加载
- 可限定到特定路径，只在代码库相关部分激活
- 例如：安全审计 skill 只在评估漏洞时加载，文档处理 skill 只在代码变更需要更新文档时加载
- 避免所有专业知识争夺上下文空间

### 4. Plugins — 分发有效方案

- 将 skills、hooks 和 MCP 配置打包成可安装的包
- 新工程师安装插件后立即拥有与老手相同的上下文和能力
- 可通过内部市场在组织内分发

### 5. MCP Servers — 扩展一切

- Claude 连接内部工具、数据源和 API 的方式
- 最成熟的团队构建了暴露结构化搜索的 MCP server
- 也可连接内部文档、工单系统或分析平台

### 额外能力

- **LSP 集成**：给 Claude 与 IDE 相同的符号级导航能力（"go to definition"、"find all references"），避免文本匹配导致的误判。对于多语言代码库，这是最高价值的投资之一
- **Subagents**：隔离的 Claude 实例，用于将探索与编辑分离。一个只读子 agent 映射子系统并写入文件，主 agent 基于全局视图进行编辑

### 扩展层总览

| 组件 | 功能 | 加载时机 | 常见错误 |
|------|------|----------|----------|
| CLAUDE.md | 自动加载的上下文文件 | 每次会话 | 把应放在 skill 中的可复用知识写在这里 |
| Hooks | 关键时刻运行的脚本 | 触发式 | 用提示词做应该自动运行的事 |
| Skills | 特定任务类型的打包指令 | 按需加载 | 把所有内容塞进 CLAUDE.md |
| Plugins | 打包的 skills/hooks/MCP 配置 | 配置后始终可用 | 让好的设置留在小圈子里 |
| LSP | 通过语言服务器的实时代码智能 | 配置后始终可用 | 假设它是自动的 |
| MCP | 外部工具和数据的连接 | 配置后始终可用 | 在基础设置完善前就构建 MCP |
| Subagents | 特定任务的独立 Claude 实例 | 按需委托 | 在同一会话中做探索和编辑 |

## 成功部署的三种配置模式

### 模式一：让代码库在规模上可导航

Claude 在大型代码库中的帮助能力，受限于其找到正确上下文的能力。过多上下文降低性能，过少则让 Claude 盲目导航。

**核心做法**：

1. **保持 CLAUDE.md 精简且分层**：根文件只放指针和关键陷阱，其余都是噪声
2. **在子目录而非仓库根目录初始化**：Claude 在被限定到实际相关的代码范围时效果最好
3. **按子目录限定测试/lint 命令**：避免 Claude 只改了一个服务却运行完整测试套件导致超时
4. **在 `.claude/settings.json` 中排除生成文件**：版本控制，团队一致
5. **构建代码库地图**：当代码不在常规目录结构中时，用轻量级 markdown 文件做目录表
6. **运行 LSP 服务器**：让 Claude 按符号而非字符串搜索

### 模式二：随模型演进积极维护 CLAUDE.md

模型在不断进化，为当前模型写的指令可能在未来模型中变得多余甚至有害。

- 为弥补特定模型限制而构建的 skills/hooks，在这些限制消失后变成开销
- **建议每 3-6 个月做一次有意义的配置审查**
- 在主要模型发布后性能似乎停滞时也值得审查

### 模式三：指定 Claude Code 管理和采用的负责人

技术配置本身不驱动采用，组织层面的投入同样重要。

- **推广最快的部署**都有在广泛开放前就投入专用基础设施建设的团队
- 负责 AI 编码工具管理的团队通常隶属于开发者体验（Developer Experience）或开发者生产力（Developer Productivity）
- 新兴角色：**Agent Manager**——混合 PM/工程师职能，专门管理 Claude Code 生态系统
- 最低可行版本：一个 **DRI**（Directly Responsible Individual），拥有 Claude Code 配置的所有权
- **建议**：尽早建立跨职能工作组（工程、信息安全、治理代表），共同定义需求和发布路线图

## 适用范围

本文假设常规软件工程环境：工程师是主要代码贡献者、使用 Git、代码遵循标准目录结构。对于游戏引擎（大型二进制资产）、非传统版本控制、非工程师贡献代码等场景，需要额外配置。
